# DeepStone

A self-hosted, web-based Hearthstone-style card game. Players register, build decks from the full card library, challenge each other or play against a simple AI, all inside the browser.

- **Engine:** [Fireplace](https://github.com/jleclanche/fireplace) — a pure-Python Hearthstone rules re-implementation (~2,500 collectible cards through the Scholomance Academy expansion).
- **Backend:** FastAPI + uvicorn + SQLite, JWT auth, WebSocket game sessions (`backend/`).
- **Frontend:** React + Vite + TypeScript (`frontend/`).
- **Deployment:** Docker Compose (`deploy/`) — intended for an Apple Silicon Mac Mini.

## Features

- Register / log in (JWT), admin user management.
- Full card gallery + deck builder with server-side deck validation (30 cards, class-legal, copy limits).
- Play vs AI or challenge another player via a shareable code/link.
- Real-time game board over WebSocket: mulligan, play cards, attack, hero powers, Discover choices.

## Running locally

Backend (port 8000):

```bash
cd backend
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
.venv/bin/python scripts/ensure_fireplace_data.py   # fetch real CardDefs.xml (git-LFS)
.venv/bin/python scripts/build_cards.py             # generate cards.json
.venv/bin/uvicorn app.main:app --port 8000
```

Frontend (port 5173, proxies to :8000):

```bash
cd frontend
npm install
npm run dev
```

Then open http://localhost:5173.

## Docker

Single-container deployment — the backend serves the built React app, the REST/WebSocket API, and card art/audio on **one port** (no nginx).

```bash
# 1. Build the frontend first (Node required) — the SPA is bind-mounted, not baked into the image
cd frontend
npm ci && npm run build
cd ..

# 2. Run (add --build to rebuild the backend image after backend code changes)
cd deploy
docker compose up -d

# site on http://<host>:8000
```

`backend/images` (card art), `backend/audio`, and `frontend/dist` are bind-mounted into the container (see `deploy/docker-compose.yml`), so you can swap assets on the host without rebuilding the image. The SQLite DB persists in a named Docker volume.

## Card art: layout & replacing images

Card art is **not** stored in git. `backend/images/` is gitignored (`.gitignore` → `**/images/`) and a pre-commit guard (`.githooks/pre-commit`) refuses commits that would add files under an `images/` directory (enable it with `git config core.hooksPath .githooks`). The default art is Blizzard's copyrighted property and must stay private.

The UI looks up art by **card ID** — e.g. `EX1_001.png` — in three subdirectories under `backend/images/`:

| Subdir        | Content              | Used by                                                   |
|---------------|----------------------|-----------------------------------------------------------|
| `cards/`      | 256px framed         | cards in hand, deck gallery, weapons — `/images/cards/{id}.png` |
| `cards_big/`  | 512px framed         | hover / large previews — `/images/cards_big/{id}.png`          |
| `cards_board/`| raw square art       | minions & heroes on the board — `/images/cards_board/{id}.png` |

Missing or tiny files fall back to a placeholder, so partial art is fine.

### Re-download the default art

```bash
cd backend
.venv/bin/python scripts/download_card_images.py            # 256 / 512 / board art for all collectible cards
.venv/bin/python scripts/download_card_images.py --tokens   # also fetch summoned-token minions
```

The script pulls from HearthstoneJSON and skips files already present (>1 KB).

### Replace with your own art

1. Find the card ID in `backend/cards.json` (generated by `scripts/build_cards.py`).
2. Drop a PNG named `{id}.png` into the matching subdir under `backend/images/`. Files must be **PNG, >1 KB** (the downloader treats ≤1 KB as missing).
3. Only have one size? Put it in `cards/` — the UI degrades gracefully. For best results provide all three sizes.

### Docker deployments

`backend/images` (and `backend/audio`, `frontend/dist`) are bind-mounted into the container. Replace files on the host and refresh the browser — no image rebuild or container restart needed.
